## Robert (code review)

- [High] `.github/workflows/ci.yml:57` — `actions/setup-node` with `cache: npm` followed by `npm ci`, but no `package-lock.json` existed in the repo. `setup-node` hard-fails ("Dependencies lock file is not found") and `npm ci` fails too, so CI could never go green on its first run.
- [High] `database/migrations/2026_09_05_163234_add_strava_columns_to_users_table.php:44` — `down()` restored `password` to `NOT NULL`, which fails on any seeded database because every user this product creates has a null password. Rollback aborted *after* dropping `sync_runs` and `activities`, leaving a half-reverted schema with the users migration still recorded as run; `migrate:refresh` was broken for the same reason.
- [Medium] `tests/Feature/Database/TrainingBlockSeederTest.php:35` — the `60 ≤ count ≤ 90` bound did not match the seeder's real 52–94 construction range. Measured at roughly 0.05 % failures per run, ~0.28 % on a Monday: random CI red about 1 run in 400.
- [Medium] `README.md:124` — "The application schedules itself daily at `STRAVA_SYNC_HOUR`" was present-tense but untrue: `routes/console.php` registers only `inspire`, and `schedule:list` reports no tasks. The README then offered `schedule:list` as a verification step that returns nothing.
- [Low] `tests/Feature/Database/TrainingBlockSeederTest.php:77` — the peak and illness assertions only checked that *some* week was the extreme, never that it was `PEAK_WEEK_INDEX` / `ILLNESS_WEEK_INDEX`. Since the seeder guarantees a strict maximum by construction, the assertion could not fail even if the shaping regressed onto the wrong week.
- [Low] `database/seeders/TrainingBlockSeeder.php:32` — `DOUBLE_RUN_WEEK_INDEXES` listed `12`, which is the peak week; the `match` dispatches week 12 to `peakWeek()`, so that entry was dead and the constant advertised three normal double-run weeks when only two existed.
- [Low] `.github/workflows/ci.yml:31` — Composer 1 cache layout (`~/.composer/cache/files`); Composer 2 on `ubuntu-latest` uses `~/.cache/composer/files`, so the cache never hit.
- [Low] `.github/workflows/ci.yml:4` — `push` is limited to `develop`/`main`, so feature-branch pushes get no CI until a PR is opened.

## Lars (security)

**No Critical and no High findings.** The controls this spec owned are correct: the allowlist parser fails closed, the `encrypted` casts sit on TEXT columns with a test that reads the raw row to prove ciphertext, both token columns are hidden, no credential of any kind is committed, `.env` is gitignored, the CI workflow uses no secrets and declares `permissions: contents: read`, and `routes/web.php` exposes only `/`.

- [Medium] `app/Models/User.php:30` — `#[Fillable]` whitelisted `strava_athlete_id` and all three token columns. `strava_athlete_id` is the key the access allowlist is checked against, so any later `$user->update($request->validated())` would let a request body rewrite the athlete identity that gates access, or plant OAuth tokens.
- [Medium] `README.md:77` — the copy-paste `.env` block ended with `STRAVA_ALLOWED_ATHLETE_IDS=10000001`, a syntactically valid and plausibly real Strava athlete id. An operator pasting the block verbatim would allowlist a third party, who could then complete the OAuth flow; the allowlist is the only access control.
- [Medium] `database/seeders/DatabaseSeeder.php:20` — `TrainingBlockSeeder` ran with no environment guard, creating a fake connected athlete and 60–90 fabricated activities. `db:seed --force` and `migrate:fresh --seed` are routine in deploy scripts, and the README recommends the latter.
- [Low] `config/strava.php:11` — `env()` coerces the literal `true` into a boolean, and `(string) true` is `'1'`, producing an allowlist of `['1']` that authorizes athlete id 1. Remote (requires an operator to write `STRAVA_ALLOWED_ATHLETE_IDS=true`) but it is a fail-open in the one control that keeps the instance private.
- [Low] `app/Models/SyncRun.php:29` — `error_message` is an unredacted TEXT column that FR-007 renders on the dashboard. Nothing writes it yet, but the natural implementation persists an HTTP exception message, which can embed the request URL and sometimes the bearer token or client secret.
- [Low] `app/Models/User.php:39` — `#[Hidden]` covers the token columns but not `strava_athlete_id`, which is the allowlist key.
- [Low] `.github/workflows/ci.yml:19` — all four third-party actions are pinned to mutable tags rather than commit SHAs. Bounded by `permissions: contents: read`, no secrets, and `pull_request` (not `pull_request_target`).
- [Low] `.env.example:4` — ships `APP_DEBUG=true`, and it is the file `composer setup` copies to `.env`. On a non-local host following the README verbatim, stack traces would render environment variables to the browser.
- [Low] `.github/workflows/ci.yml:55` — `composer audit` covers PHP dependencies, but the job runs `npm ci` and `npm run build` with no `npm audit`.
- [Low] `public/robots.txt:2` — empty `Disallow:` invites full crawling of an instance the README describes as private. Pre-existing from the skeleton, outside this branch's diff.
- [Note] `SECURITY.md` / `public/.well-known/security.txt` — absent, and not in scope for this spec: both are disclosure affordances for internet-facing services with third-party users. Revisit at ship time if the app lands on a public domain.

**Open (Low) — deliberately not changed in this spec:**

- `SyncRun::error_message` redaction — nothing writes the column yet. **This is a requirement for the sync spec:** the exception message must be scrubbed of URLs, bearer tokens and the client secret before it is persisted or rendered.
- `strava_athlete_id` not in `#[Hidden]` — the product is Blade-only with no JSON API surface, and `TrainingBlockSeederTest` relies on it being serialized. Revisit if an API route is ever added.
- Actions pinned to tags rather than SHAs — bounded by read-only permissions, no secrets, and `pull_request` rather than `pull_request_target`.
- No `npm audit` step — `npm audit` fails noisily on transitive dev advisories and would make CI red for issues outside this product's control.
- `APP_DEBUG=true` in `.env.example` — stock Laravel skeleton content; the PRD records no deploy target yet. **Flag for `larapilot-ship`:** the production `.env` must set `APP_DEBUG=false`.
- `public/robots.txt` — pre-existing skeleton file, outside this branch's diff. Worth tightening when a deploy target exists.
- CI `push` scoped to `develop`/`main` — matches the trigger design the plan specified; PRs to those branches still run every gate, and there is no remote configured yet.
